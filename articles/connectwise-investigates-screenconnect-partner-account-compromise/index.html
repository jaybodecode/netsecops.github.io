Executive Summary

ConnectWise, a leading provider of software for Managed Service Providers (MSPs), has confirmed it is investigating a security incident involving its ScreenConnect remote access solution. Reports indicate that threat actors have gained unauthorized access to the accounts of ConnectWise partners (MSPs) and are using that access to deploy malicious software to the MSPs' downstream customers. This constitutes a significant supply chain attack, leveraging the trusted relationship between MSPs and their clients. Due to the administrative power of Remote Monitoring and Management (RMM) tools like ScreenConnect, this compromise poses a severe risk, potentially enabling widespread, simultaneous intrusions across numerous organizations.

Threat Overview

On November 11, 2026, ConnectWise acknowledged the incident after receiving reports from its partners about unauthorized activity. The core of the issue is the compromise of ScreenConnect accounts belonging to MSPs. Once attackers gain control of an MSP's ScreenConnect instance, they inherit the MSP's administrative access to all of their clients' managed endpoints.

The attackers are exploiting this powerful, trusted access to deploy unauthorized remote-access software within customer environments. This creates a secondary, persistent backdoor that the attacker controls directly, bypassing the MSP's infrastructure. While ConnectWise has not yet confirmed the initial access vector used to compromise the partner accounts, security researchers suspect that vulnerable third-party extensions installed within the ScreenConnect platform may be the root cause.

Technical Analysis

This attack leverages the inherent trust and power of RMM platforms, which are considered 'Tier 0' assets because they provide pervasive administrative control.

  1. Initial Access: The initial vector is suspected to be the exploitation of a vulnerability in a third-party extension for ScreenConnect. This would fall under T1195.002 - Compromise Software Supply Chain. Alternatively, if partner credentials were stolen through other means like phishing, it would be T1078 - Valid Accounts.
  2. Execution & Lateral Movement: By using the legitimate functionality of ScreenConnect, attackers can execute commands and deploy software across all managed endpoints. This is a classic example of T1219 - Remote Access Software. The attackers are not breaking into each customer network individually; they are using the RMM as a force multiplier to pivot from one MSP to many clients.
  3. Persistence: The deployment of a secondary, unauthorized remote access tool is a key step for the attackers. This ensures they maintain access to the customer environment even if the compromised ScreenConnect account is discovered and remediated. This aligns with T1105 - Ingress Tool Transfer and T1574.002 - Hijack Execution Flow: DLL Side-Loading if the tool is deployed in a stealthy manner.

Impact Assessment

The compromise of an RMM platform is one of the most impactful types of cyberattacks due to its cascading effects.

  • Widespread Customer Compromise: A single MSP breach can lead to the simultaneous compromise of hundreds or thousands of downstream customers, regardless of their own security posture.
  • High-Privilege Access: RMM tools operate with system-level privileges, giving attackers immediate administrative control over compromised endpoints. This allows for data exfiltration, ransomware deployment, and further lateral movement within the customer's network.
  • Systemic Risk to the MSP Ecosystem: Attacks like this undermine the trust-based model of managed services. Businesses rely on their MSPs for security, and when that trust is broken, it has far-reaching consequences for the entire industry.
  • Operational Disruption: Both the MSP and its clients face significant disruption as they work to identify, contain, and remediate the breach across potentially thousands of systems.

Detection & Response

  1. Audit RMM Sessions: All organizations using ScreenConnect or similar RMM tools must rigorously audit all administrative sessions. Look for logins from unfamiliar IP geolocations, sessions with unusual durations, and commands executed that are outside the norm for your technicians. This aligns with D3FEND's D3-RAPA: Resource Access Pattern Analysis.
  2. Inventory Extensions: MSPs should immediately create an inventory of all third-party extensions installed on their ScreenConnect servers. Check for any unauthorized or recently added extensions and research their reputation.
  3. Endpoint Monitoring: Customers of MSPs should have their own EDR and logging capabilities. Monitor for the installation of new software and the execution of scripts by the RMM agent. Alert on any activity that seems suspicious or is not part of a scheduled maintenance task.
  4. Account Security: Enforce MFA on all RMM accounts. Regularly review user accounts and permissions, disabling any that are no longer needed.

Mitigation

  1. Harden RMM Platforms: Treat your RMM platform as a Tier 0 asset. Restrict access to the management console to specific IP addresses. Enforce mandatory MFA for all users. This is an application of D3-ACH: Application Configuration Hardening.
  2. Vet Third-Party Extensions: Implement a strict policy for vetting and approving any third-party extensions. Only install extensions from reputable developers and, if possible, review their code for security flaws. This falls under M1033 - Limit Software Installation.
  3. Principle of Least Privilege: Configure RMM roles and permissions to grant technicians only the access they need. Avoid using a single, highly privileged account for all operations.
  4. Customer-Side Validation: End customers should not blindly trust all activity from their MSP's RMM tool. Use on-premises security tools to monitor the RMM agent's behavior and alert on actions that fall outside of the agreed-upon service contract, such as the installation of unknown software.

D3FEND Defensive Countermeasures

Multi-factor Authentication

D3-MFAMaps to MITREM1032
D3FEND

The most effective preventative measure against account takeover is the enforcement of multi-factor authentication (MFA) on all ScreenConnect accounts, especially those with administrative privileges. Even if an attacker manages to steal a partner's password through phishing or other means, MFA provides a critical second barrier to entry. MSPs must mandate non-phishable MFA methods, such as FIDO2 security keys or authenticator apps, for all technicians and administrators. This single control dramatically increases the difficulty for an attacker to gain unauthorized access to the RMM platform, thereby protecting the entire downstream customer base from this type of supply chain attack.

Resource Access Pattern Analysis

D3-RAPAMaps to MITREM1040
D3FEND

To detect an active compromise, MSPs must perform continuous analysis of RMM resource access patterns. This involves ingesting ScreenConnect audit logs into a SIEM and establishing a baseline of normal activity for each technician account. Alerts should be configured for deviations from this baseline, such as logins from new or unusual IP addresses/geolocations, access outside of normal working hours, or an abnormally high number of remote sessions. Furthermore, analyzing the types of commands executed during sessions can reveal malicious intent. For example, a technician who normally only performs patching suddenly running discovery scripts or attempting to download files would be highly suspicious. This behavioral analysis can provide early warning of an account takeover.

Application Configuration Hardening

D3-ACHMaps to MITREM1054
D3FEND

MSPs must harden the configuration of their ScreenConnect instances. This includes restricting administrative access to the server console to a whitelist of trusted IP addresses, effectively preventing logins from the open internet. Additionally, a strict vetting process for all third-party extensions must be implemented. Each extension should be reviewed for security and business need before being installed. Disabling or removing unused or risky extensions reduces the attack surface of the platform. Finally, role-based access control (RBAC) should be meticulously configured to ensure technicians have only the minimum necessary privileges to perform their jobs, limiting the potential damage if an account is compromised.
