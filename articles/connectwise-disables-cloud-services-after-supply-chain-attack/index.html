Executive Summary

On October 17, 2026, IT management software provider ConnectWise suspended its Cloud Backup services in response to a significant supply chain attack. Threat actors exploited a compromised application credential associated with the ConnectWise Cloud Backup service (formerly SkyKick) to gain unauthorized access to customer Microsoft 365 tenants. This allowed the attackers to bypass standard user authentication, including MFA, and inherit the application's broad permissions to access sensitive data. The incident has impacted Managed Service Providers (MSPs) and their downstream customers, prompting ConnectWise to disable multiple application identities to contain the threat. The initial access vector for the credential compromise remains under investigation.

Threat Overview

The attack began around October 15, 2026, when an unknown threat actor started using a compromised OAuth application credential for the ConnectWise Cloud Backup application (App ID: 506e08f9-6e9a-4da4-942b-a099a03644ae). By authenticating as this trusted application, the attackers circumvented user-level security controls and gained access to Microsoft 365 environments with the permissions granted to the app. These permissions often include access to emails, SharePoint, Teams, and other sensitive directory data.

Security firm Huntress reported observing unauthorized sign-ins across 173 partner and customer tenants, originating from the IP address 144.172.64.128. The attack is a classic example of abusing the trust model of third-party application integrations in cloud environments, turning a legitimate, highly-privileged application into a powerful attack tool.

Technical Analysis

The attack chain leverages the inherent trust between a Microsoft 365 tenant and its integrated third-party applications. The threat actor's tactics, techniques, and procedures (TTPs) include:

  1. Initial Access - Steal Application Access Token (T1528): The attackers obtained the credentials for the ConnectWise Cloud Backup application. The method of this initial compromise is currently unknown.
  2. Defense Evasion - Valid Accounts: Cloud Accounts (T1078.004): By using the legitimate, albeit stolen, application credentials, the attackers' sign-ins appeared as legitimate service-to-service communication, bypassing user-centric defenses like MFA.
  3. Privilege Escalation & Persistence - Additional Cloud Credentials (T1098.001): In at least one observed case, the attackers used the initial access to elevate the privileges of a related ConnectWise Cloud Management application to Global Administrator. They then added new client secrets to other applications within the tenant, creating multiple backdoors for persistent access.
  4. Collection - Email Collection (T1114.002): With access to the tenants, the attackers had the capability to access and exfiltrate data from various Microsoft 365 services, including Outlook, SharePoint, and Teams.

This attack highlights the critical risk posed by over-privileged OAuth applications in enterprise environments.

Impact Assessment

The business impact of this supply chain attack is severe. For MSPs, it erodes trust and creates a significant security liability for all their downstream customers. The suspension of Cloud Backup, SaaS Security, and Cloud Management services causes operational disruption, preventing new backups and security management tasks. For affected customers, the breach means potential exposure of all data within their Microsoft 365 environment. Since the attack bypasses user MFA, organizations that believed they were secure are vulnerable. The costs of incident response, forensic analysis, and potential data loss are substantial for all parties involved.

Cyber Observables — Hunting Hints

Security teams may want to hunt for the following patterns to detect related activity:

  • Azure AD Sign-in Logs: Search for all sign-ins (interactive and non-interactive) where the appId is 506e08f9-6e9a-4da4-942b-a099a03644ae and the source IP is not from a known service range.
  • Azure AD Audit Logs: Hunt for privilege escalation activities. Filter for operations like Add-AzureADApplicationOwner, Add service principal credential, or Add owner to application where the initiating user/principal is an application, especially one related to ConnectWise.
  • Anomalous Application Behavior: Look for applications granting themselves or other applications new Application.ReadWrite.All or Directory.ReadWrite.All permissions.

Detection & Response

Defenders should implement the following detection and response strategies:

  1. Audit Application Permissions: Regularly review all applications integrated into your Microsoft 365 tenant, paying close attention to those with high-level permissions like Mail.ReadWrite.All, Files.ReadWrite.All, or Directory.ReadWrite.All. Use Microsoft's built-in tools or third-party solutions to assess application risk.
  2. Monitor Sign-in Logs: Implement SIEM rules to alert on suspicious sign-in patterns for service principals, such as sign-ins from unusual IP addresses, locations, or an impossible travel scenario. This can be achieved through Network Traffic Analysis (D3-NTA).
  3. Track Privilege Changes: Create high-priority alerts for any event where an application elevates its own privileges or modifies the credentials of another application. This is a strong indicator of compromise. This involves Domain Account Monitoring (D3-DAM).
  4. Incident Response Playbook: If a compromised application is detected, the playbook should include steps to immediately disable the application, revoke its credentials and permissions, and initiate a forensic investigation to determine the scope of the breach.

Mitigation

To mitigate the risk of similar attacks, organizations should adopt a defense-in-depth approach to cloud application security:

  1. Least Privilege Principle: When granting consent to third-party applications, only approve the minimum permissions necessary for the application to function. Avoid blanket approvals for highly permissive scopes. This is a form of Application Configuration Hardening (D3-ACH).
  2. Vendor Risk Management: Thoroughly vet the security practices of any third-party vendor before integrating their applications into your environment. This includes reviewing their security certifications and incident response plans.
  3. Conditional Access Policies for Applications: Where possible, apply Conditional Access policies to service principals to restrict access based on IP range or other factors. This can help limit the blast radius if an application credential is compromised.
  4. Regular Audits: Conduct quarterly or semi-annual reviews of all enterprise applications and their permissions. Remove any applications that are no longer in use or have excessive permissions.

D3FEND Defensive Countermeasures

Application Configuration Hardening

D3-ACHMaps to MITREM1054
D3FEND

In the context of the ConnectWise breach, Application Configuration Hardening is critical for mitigating the risk of compromised OAuth applications. Organizations must move beyond default settings and proactively manage the permissions of all third-party applications integrated with Microsoft 365. A key step is to conduct a thorough audit of all existing enterprise applications and service principals. Identify applications with high-risk permissions such as Application.ReadWrite.All, Directory.ReadWrite.All, Mail.ReadWrite.All, and Files.ReadWrite.All. For each, validate the business justification for these permissions. If the justification is weak or the permission is not actively used, revoke it immediately. Implement a 'least privilege' policy for any new application integrations, denying requests for excessive permissions. Utilize tools like Microsoft's App Governance in Defender for Cloud Apps to automate the discovery, monitoring, and remediation of risky OAuth applications. This proactive hardening significantly reduces the potential blast radius if an application's credentials are stolen, as the compromised app will have fewer permissions to abuse.

Domain Account Monitoring

D3-DAMMaps to MITREM1047
D3FEND

Domain Account Monitoring, when applied to cloud environments like Azure AD, is essential for detecting the malicious activity seen in the ConnectWise attack. Security teams should configure specific monitoring and alerting rules focused on the lifecycle and behavior of service principals, not just user accounts. This involves ingesting Azure AD audit and sign-in logs into a SIEM. Create high-severity alerts for events such as: 1) A service principal adding a new credential (password or certificate) to itself or another application. 2) A service principal elevating its own privileges or granting high-level permissions like Global Administrator to another principal. 3) A service principal signing in from a geographic location or IP address that deviates from its established baseline. By establishing a baseline of normal application behavior and monitoring for these specific deviations, organizations can detect the TTPs used by attackers to escalate privileges and establish persistence after an initial application compromise. This moves detection beyond just the initial access and provides opportunities to interrupt the attack chain.

Resource Access Pattern Analysis

D3-RAPAMaps to MITREM1040
D3FEND

Resource Access Pattern Analysis is a crucial defense against the data access abuse demonstrated in this supply chain attack. The goal is to baseline the normal data access patterns of service applications like ConnectWise Cloud Backup and alert on significant deviations. For example, a backup application might normally access large volumes of data during scheduled backup windows. However, it would be highly anomalous for this same application to start accessing a wide range of mailboxes or SharePoint sites it has never touched before, especially outside of a backup context. Security teams can use tools like Microsoft Purview or Defender for Cloud Apps to monitor and analyze application access to sensitive data. Configure policies that alert when a service principal accesses an unusually high number of files, accesses data at an anomalous time of day, or accesses data from a type of resource (e.g., executive mailboxes) it normally doesn't interact with. This provides a critical detection layer that can identify a compromised application even if the initial sign-in appears legitimate.
